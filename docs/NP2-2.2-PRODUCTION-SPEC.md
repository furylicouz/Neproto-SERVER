# NP/2 v2.2 Production Protocol

Status: approved for implementation by the owner on 2026-07-18

Date: 2026-07-18

## 1. Outcome

NP/2 v2.2 is the production evolution of the existing NP/2 v2.1 system. It is
not a throwaway MVP and it is not wire-compatible with VLESS, Trojan, SOCKS,
Shadowsocks, or Hysteria. The release must provide:

- full TCP and UDP forwarding for IPv4 and IPv6;
- direct iOS Packet Tunnel integration without a loopback SOCKS dependency;
- Windows and Linux client adapters and an Ubuntu server;
- reliable HTTPS compatibility transport plus UDP-capable WebRTC and HTTP/3
  transports;
- bounded adaptive flow control, cover scheduling, resource accounting, and
  production observability;
- rolling migration from already deployed NP/2 v2.1 clients;
- reproducible correctness, load, loss, migration, and traffic-analysis tests.

Android is not part of the v2.2 client release. It can consume the same public
protocol after the iOS, Windows, Linux, and server implementations pass the
release gates in this document.

## 2. Non-goals

- Claiming that NP/2 is invisible to DPI or categorically stronger than
  VLESS + REALITY/XHTTP, Hysteria2, or Trojan without comparative evidence.
- Sending arbitrary bytes outside a standards-compliant outer carrier.
- Inventing cryptographic primitives. NP/2 keeps HKDF-SHA-256,
  HMAC-SHA-256, and ChaCha20-Poly1305.
- Encrypting traffic beyond the NP/2 exit server. End-to-end application
  encryption such as HTTPS remains the responsibility of the application.
- Breaking or silently reinterpreting the NP/2 v2.1 base cell protocol.

## 3. Compatibility contract

### 3.1 Invariants

The following v2.1 wire behavior is frozen:

1. The authentication challenge version remains `2`.
2. The existing handshake messages and known feature bits remain unchanged.
3. `NewTypeMap` continues to map exactly the existing twelve base cell kinds.
4. TCP `OPEN`, `OPEN_OK`, `DATA`, `FIN`, `RESET`, and `WINDOW_UPDATE`
   semantics remain unchanged.
5. A v2.1 peer can connect to a v2.2 peer and use TCP without understanding
   any v2.2 extension.

Adding a value before the existing `CellKindCount` is prohibited. A golden
compatibility test must prove that fixed v2.1 header-map seeds generate the
same type maps and encoded cells after every v2.2 change.

### 3.2 Extension negotiation

Extensions are negotiated after the authenticated, per-cell-AEAD-protected
multiplexer starts. This avoids adding an unknown handshake feature bit that
would cause released v2.1 clients to reject the server challenge.

The existing connection-level `PROFILE` cell is the extension control
envelope. Existing peers already ignore this cell, so the extension is
additive.

The payload is canonical and bounded by the existing cell limits:

```text
extension_envelope =
    magic[4]            // ASCII "NPEX"
    envelope_version[1] // 0x01
    message_type[1]     // 0x01 OFFER, 0x02 ACCEPT, 0x03 UPDATE
    message_id[uvarint]
    tlv_count[uvarint]
    repeated TLV

TLV =
    type[uvarint]
    length[uvarint]
    value[length]
```

Rules:

- uvarints use the existing NP/2 canonical encoding.
- TLVs are strictly ascending by type and may not repeat.
- Unknown optional TLVs are ignored. Unknown mandatory TLVs, indicated by bit
  62 of the TLV type, reject only the extension negotiation, not the legacy
  TCP session.
- The server sends `OFFER`; the client sends one `ACCEPT` containing a subset.
- A duplicated or stale `message_id` is ignored. A conflicting reuse is a
  session protocol violation.
- No UDP association may open before the datagram capability is accepted.
- A profile may set `require_datagrams=true`. In that mode the iOS client must
  fail before installing default routes if the server does not complete the
  negotiation within the bounded startup deadline.

Initial registered TLVs:

| Type | Name | Encoding | Limit |
|---:|---|---|---:|
| 1 | capabilities | uint64 big-endian bitset | fixed 8 bytes |
| 2 | max_udp_associations | canonical uvarint | 1..4096 |
| 3 | max_udp_payload | canonical uvarint | 1200..65507 |
| 4 | udp_idle_timeout_ms | canonical uvarint | 5000..600000 |
| 5 | max_session_receive_bytes | canonical uvarint | 1 MiB..256 MiB |
| 6 | max_stream_window_bytes | canonical uvarint | 64 KiB..16 MiB |
| 7 | unreliable_datagram_bytes | canonical uvarint | 0 or 512..65507 |

Capability bits:

| Bit | Capability |
|---:|---|
| 0 | UDP associations over reliable NP/2 cells |
| 1 | unreliable carrier datagram fast path |
| 2 | adaptive stream-window updates |
| 3 | carrier migration without profile recreation |
| 4 | Mosaic adaptive cover scheduling |

Bit 4 changes only the local sender's padding, dummy-cell, and bounded-delay
policy after authenticated extension negotiation. Its normative behavior and
legacy-peer fallback are defined in
[`NP2-MOSAIC-SPEC.md`](NP2-MOSAIC-SPEC.md).

## 4. Destination commands

The first byte of existing `OPEN` metadata is promoted from a fixed TCP marker
to a command:

| Value | Command | Remaining metadata |
|---:|---|---|
| `0x01` | TCP_CONNECT | existing canonical target |
| `0x02` | UDP_FIXED | one canonical target |
| `0x03` | UDP_ASSOCIATE | empty; each datagram carries its own target |

Address encodings remain the existing canonical domain, IPv4, and IPv6 forms.
An old server rejects `0x02` and `0x03` with address-not-supported and keeps the
session alive.

The server applies the same destination policy to TCP targets, fixed UDP
targets, every unbound UDP destination, and every DNS resolution result.
Private, loopback, link-local, multicast, documentation, benchmark, and other
denied special ranges remain blocked unless an explicit administrator policy
allows them.

## 5. UDP association protocol

One logical NP/2 stream is one UDP association. `OPEN_OK` means the server has
allocated the UDP socket and installed resource accounting. `OPEN_FAIL` means
no datagram may be sent.

The reliable representation inside `DATA` is a sequence of bounded records:

```text
udp_record =
    record_type[1]       // 0x01 DATAGRAM, 0x02 ERROR, 0x03 CLOSE
    packet_id[uvarint]   // monotonically increasing per direction
    flags[1]
    [target]             // required for UDP_ASSOCIATE
    payload_length[uvarint]
    payload[payload_length]
```

Rules:

- `payload_length` is at most the negotiated `max_udp_payload` and never above
  65507 bytes.
- Record decoders allocate only after validating the complete bounded length.
- Empty UDP payloads are valid.
- Packet IDs may not repeat within a live association. A repeat is dropped and
  counted; it does not terminate unrelated TCP streams.
- A reliable carrier preserves records exactly but can introduce head-of-line
  latency. It is the compatibility path, not the preferred real-time path.
- The receiver may drop UDP records under queue pressure. It must never apply
  TCP-style unbounded backpressure to the complete NP/2 session.
- `ERROR` contains a stable one-byte reason and optional sanitized text capped
  at 128 bytes. It never contains server filesystem or internal addresses.
- Association idle timeout is refreshed only by real UDP records, not dummy
  cover traffic.

### 5.1 Unreliable fast path

If capability bit 1 is accepted and the carrier implements `DatagramCarrier`,
the same association can send individual UDP records outside the ordered cell
stream. The datagram payload starts with the association stream ID followed by
the `udp_record` body. It receives independent directional ChaCha20-Poly1305
protection using HKDF labels distinct from reliable cell keys.

The fast path does not fragment. A record larger than the carrier's current
maximum datagram size is sent through the reliable representation. This avoids
unbounded fragment reassembly and follows QUIC DATAGRAM semantics, where the
application must handle the path-dependent maximum size.

The WebRTC implementation uses a second unordered data channel with zero
retransmissions. The HTTP/3 implementation is the WebTransport Extended
CONNECT carrier defined by
[`ADR-002`](decisions/ADR-002-webtransport-http3-carrier.md): one authenticated
bidirectional WebTransport stream carries reliable NP/2 messages and
WebTransport datagrams carry the unreliable path. Both paths remain
congestion-controlled by their carrier.

`CarrierHTTP3` has the stable carrier-kind value `3`. Its reliable stream starts
with one zero byte to activate QUIC's lazily opened stream, then uses a
four-byte unsigned big-endian message length followed by exactly that many
bytes. Zero-length and oversized messages are protocol violations. This
framing exists only inside the WebTransport session; no bytes are appended
outside QUIC or HTTP/3.

## 6. TCP flow control and memory safety

The 16 MiB protocol maximum remains unchanged. Production defaults are
negotiated within administrator caps:

- initial stream window: 2 MiB;
- minimum adaptive window: 256 KiB;
- maximum production stream window: 8 MiB;
- maximum aggregate unread bytes per session: configurable, default 64 MiB;
- maximum active TCP streams: configurable, default 128;
- maximum UDP associations: configurable, default 256.

Window growth uses measured delivery rate and RTT to estimate bandwidth-delay
product. Growth is gradual and may not reserve memory beyond the session
budget. Shrinking applies only to new credit; already advertised credit is
honored. `WINDOW_UPDATE` remains additive and coalesced.

The scheduler must prevent one stream, UDP association, or dummy queue from
starving connection control cells. Priorities are:

1. authentication/lifecycle and flow-control cells;
2. interactive TCP and DNS datagrams;
3. ordinary TCP data and ordinary UDP;
4. padding and dummy cover traffic.

## 7. Carrier selection and migration

Production carrier order is adaptive, not hard-coded:

1. use the last successful carrier while its network-scoped cache is fresh;
2. otherwise race HTTP/3 and WebRTC with a bounded stagger;
3. start HTTPS/WebSocket fallback without waiting for the sum of both UDP
   carrier timeouts;
4. authenticate every candidate and keep only the first policy-compliant
   success;
5. close losing candidates and account for all resources.

HTTP/3 is attempted only when the client profile contains an `http3_url` and
the server has the independent `enable_http3` feature flag enabled. Removing
the URL or disabling the flag is an immediate operational kill switch and does
not change the v2.1 compatibility path.

The HTTPS/WebSocket carrier stays supported for networks that block UDP. UDP
application traffic still works through its reliable association path.

An iOS Wi-Fi/cellular transition first attempts carrier-native path migration.
If that fails, it creates a new authenticated session, stops accepting new
flows on the old session, drains bounded existing TCP flows, and switches the
default data plane. A failed migration must not leave a default route pointing
at a dead Packet Tunnel data plane.

## 8. Cover traffic and traffic-analysis claims

Cover behavior is a measured scheduler, not unrestricted random bytes:

- padding and dummy bytes remain inside valid carrier messages;
- each profile has explicit latency and bandwidth budgets;
- bulk data uses bounded bursts instead of an independent sleep before every
  real cell;
- the scheduler records useful bytes, padding, dummy bytes, queue delay, and
  budget drops without recording payloads or destinations;
- no production claim may exceed the evidence required by ADR-001.

HTTP/3, WebRTC, and HTTPS are separate observable populations and must have
separate classifier baselines. A unique stable NP/2 pattern is treated as a
potential fingerprint, not automatically as an advantage.

## 9. Security and abuse controls

- Mandatory inner AEAD remains required for every authenticated session.
- Reliable and unreliable directions use independent keys and nonce spaces.
- Nonce counters are 64-bit, never reused, and close only the affected session
  before exhaustion.
- UDP egress is created only after authenticated user identification.
- Per-user and global limits cover sessions, TCP connections, UDP
  associations, packets per second, bytes per second, DNS rate, and target
  creation rate.
- The server applies anti-amplification accounting: before a UDP target has
  replied, server-to-client bytes for that target may not exceed three times
  the authenticated client-to-server bytes plus one path-MTU allowance.
- Queue overflow drops UDP first and increments a metric; it never grows
  memory without a bound.
- Logs redact credentials, secrets, payloads, private paths, and destination
  names/addresses. Optional destination auditing is a separate explicit
  administrator mode and is disabled by default.
- 0-RTT application data is disabled for NP/2 v2.2. Resumption may be specified
  later with replay-safe commands only.
- The WebTransport dependency must be version `v0.10.0` or newer because older
  releases contain CVE-2026-21434, an unauthenticated memory-exhaustion issue.
  The pinned release is checked by dependency and vulnerability scanning.
- Independent protocol and cryptographic review is a release gate for public
  claims, even after internal tests pass.

## 10. Observability

Every session exposes bounded counters and histograms:

- carrier attempts, selected carrier, connect and authentication latency;
- useful TCP/UDP bytes, outer bytes, padding, and dummy bytes;
- RTT, flow-control stalls, send queue and receive queue delay;
- active/retired streams and UDP associations;
- UDP drops by reason, oversized fallback, policy rejects, and idle expiry;
- reconnects, migrations, network changes, and sanitized terminal reason;
- process CPU, resident memory, goroutines, open descriptors, and sockets.

The iOS diagnostic screen shows sanitized state and recent terminal errors.
The server exposes Prometheus-format metrics on a loopback-only listener and
structured JSON logs to journald/stdout.

## 11. Production release gates

### 11.1 Correctness

- Unit, property, fuzz, and race tests pass for handshake, type map, control
  envelope, TCP streams, UDP records, AEAD, policy, and shutdown.
- A golden test proves v2.1 handshake, type-map, and TCP cell compatibility.
- IPv4/IPv6 TCP and UDP work from physical iPhone, Windows, and Linux clients.
- DNS works over UDP and TCP, including truncated UDP responses that retry TCP.
- Packet loss, duplication, reordering, MTU reduction, Wi-Fi/cellular changes,
  server restart, and carrier fallback have deterministic test coverage.

### 11.2 Performance SLO

On the recorded physical iPhone path where direct throughput is about
100 Mbit/s and RTT is 100–180 ms:

- useful download p50 is at least 40 Mbit/s on HTTP/3 or WebRTC;
- useful download p10 is at least 20 Mbit/s;
- HTTPS compatibility fallback reaches at least 20 Mbit/s;
- cold connection p95 is below 5 seconds and cached connection p95 below
  2 seconds;
- the `web` profile remains within its configured 30% cover cap;
- a 30-minute run has no monotonic goroutine, association, descriptor, or
  resident-memory growth after traffic stops.

If the external cellular path cannot deliver these values directly during the
same test window, results are normalized against the simultaneous direct-path
baseline: NP/2 fast carriers must reach at least 60% of direct useful
throughput and HTTPS fallback at least 30%.

### 11.3 Capacity and reliability

- The current 2-vCPU/2-GiB server sustains 100 authenticated sessions, 5,000
  aggregate TCP streams, and 10,000 aggregate UDP associations in staged load
  tests without exceeding configured memory or descriptor limits.
- Session setup and target-dial failure do not leak resources.
- Rolling server deployment keeps v2.1 TCP clients operational.
- A failed new release has a tested rollback that preserves credential and
  QR/onboarding data.

### 11.4 Traffic-analysis validation

- Reproducible captures exist for Safari HTTP/3, Safari WebSocket, a normal
  WebRTC call/data workload, NP/2 carriers, and chosen VLESS/Hysteria/Trojan
  baselines under matched payloads.
- Reports compare TLS/QUIC fingerprints, SNI/ALPN, packet-size distributions,
  bursts, loss response, lifetime, throughput, CPU, memory, and cover cost.
- Active probes receive only a valid decoy response or a bounded generic
  failure and cannot allocate target sockets before authentication.

## 12. Deployment and migration

1. Ship observability and v2.1 golden tests without changing the wire.
2. Deploy a dual-capable server that still advertises the original handshake
   features and sends the protected v2.2 extension offer after authentication.
3. Release Windows/Linux test clients, then an iOS beta profile with
   `require_datagrams=false`.
4. Enable reliable UDP associations and verify abuse limits.
5. Enable WebRTC unreliable datagrams, then HTTP/3, behind independent server
   feature flags.
6. Turn on adaptive carrier racing and migration only after soak tests.
7. Make `require_datagrams=true` the default only after the production server
   fleet has completed the dual-capable rollout.
8. Keep the v2.1 TCP path for at least one full client release cycle. Removal
   requires a separate deprecation decision and usage evidence.
