## 1. Executive Summary
━━━━━━━━━━━━━━━━━━━━

NP/2 0.4.0 now contains an authoritative Constellation master, SSH-enrolled
data-plane nodes, authenticated NP/2 inter-node TCP/UDP relay, bounded two-hop
chains, signed per-user server catalogues, administrator and client routes,
credential synchronization, cluster status in `np`, and an iOS multi-server
and route workflow.

The local, Linux-container and unsigned-iOS gates pass. The race detector found
one concurrent map write in cluster health probing; it was fixed and the exact
test subsequently passed under `-race`.

This evidence supports an RC artifact. A two-VPS canary, clean-host SSH
enrolment, signed physical-device test and rollback drill remain mandatory
before calling the cluster live or production-proven.

## 3. Risks

| Area | Issue | Impact | Severity | Recommendation |
|---|---|---|---|---|
| External SSH | Unit/fake-host coverage cannot prove every VPS image, firewall and SSH policy | Enrolment can fail on a real provider | 🟡 Medium | Canary on a clean supported VPS and retain its console access |
| Remote rollback | A failed master commit leaves the previous remote installation active rather than uninstalling it | Manual cleanup can be required | 🟡 Medium | Display the isolated node as unpublished and provide an explicit repair/remove runbook |
| Mobile domains | TUN sees numeric IP destinations; domain-only local rules lack a trusted name-to-IP binding | Visible rule may not affect a flow | 🟡 Medium | Add DNS/FakeIP mapping before claiming domain-rule enforcement |
| Health status | Panel `UP` currently represents TCP endpoint reachability; enrolment attestation is the stronger authenticated check | A reachable but unhealthy peer can look available | 🟡 Medium | Add periodic authenticated NP/2 health telemetry |
| Device gate | Unsigned build does not prove entitlement, NetworkExtension lifecycle or real radio routing | Device-only failure remains possible | 🟠 High | Complete signed iPhone connect/switch/route/reconnect test |
| Multi-site gate | Localhost/container routing does not reproduce provider routing, MTU, loss and NAT | Real throughput/reliability can differ | 🟠 High | Complete a two-VPS TCP/UDP canary before rollout |

## 4. Recommendations

1. Treat this archive as RC1 and do not overwrite the current production node.
2. Enrol one disposable edge through `np` using a verified host fingerprint.
3. Test direct, selected-node and two-hop routes for both TCP and UDP.
4. Publish the edge to one test user, refresh the signed iOS catalogue, switch
   servers, add/remove a CIDR route, revoke access and confirm fail-closed
   behaviour.
5. Run the documented backup/rollback drill before widening access.
