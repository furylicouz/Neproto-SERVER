## 1. Executive Summary

The measured bottleneck was carrier selection, not NP/2 encryption, framing,
Mosaic cover, or the iOS userspace data plane. On the tested Mac-to-VPS route,
UDP throughput collapses above roughly 10 Mbit/s, so the previous auto policy
selected a healthy but slow HTTP/3 session. The same NP/2 data plane over HTTPS
reaches the direct route's throughput.

All runtime clients now default to the performance-first order `HTTPS ->
HTTP/3 -> WebRTC`; iOS serializes it explicitly for initial connection and
network migration. An explicit `udp-first` policy preserves the authenticated
carrier race for routes where measurements favor UDP. Every fallback still
requires complete NP/2 authentication and v2.2 extension negotiation. Cell
AEAD and Mosaic are unchanged.

### Physical iPhone LTE follow-up

The signed iOS build was installed on the physical `Furylicouz` device and the
Packet Tunnel remained active throughout the controlled measurements. The
active carrier was HTTPS and the server-side outer socket was measured directly
with Linux TCP telemetry.

| Measurement | Evidence | Result |
|---|---|---:|
| NP/2 Safari workload | Main 60.9 MB / 15 s download interval | 32.5 Mbit/s average; about 50-54 Mbit/s one-second peak |
| Direct VPS-to-iPhone control | Same VPS and LTE path, 50 MB incompressible HTTPS resource, tunnel route excluded | 44.1 Mbit/s with BBR |
| Direct control with CUBIC | Same resource, endpoint, phone, and test sequence | 30.4 Mbit/s; 779,941 retransmitted bytes |
| Direct control with BBR | 50,282,986 bytes sent in 9.071 s; 104,100 retransmitted bytes | About 45% faster than CUBIC |
| Packet Tunnel CPU profile | 810 ms CPU sampled over 30 s | About 2.7% of one core |
| Completed NP/2 session | 192,012,474 sent payload bytes; 93,944 cell-framing bytes; 3,690,520 padding bytes; 161,184 dummy bytes | About 2.05% total NP/2 cover and framing overhead |
| Flow control | 390 stalls over about 192 MB of server-to-client payload while the kernel send queue remained populated | Not the primary throughput limiter |

The remaining ceiling on this LTE sample is primarily the VPS-to-mobile route,
not cell encryption or the iOS userspace data plane. During load the NP/2
carrier filled the kernel send queue while BBR reported roughly 32-47 Mbit/s
delivery estimates and large transient RTT growth. BBR plus `fq` is therefore
installed by the server bundle for supported Linux kernels and was persisted on
the production node. The installer retains the host TCP defaults when BBR is
not available.

## 2. Findings

| Area | Evidence | Result | Severity | Resolution |
|---|---|---:|---|---|
| Old mobile carrier policy | Same 25 MB download selected HTTP/3 | 18.51 / 17.96 Mbit/s | 🟠 High | Replaced mobile auto selection with performance-first ordering |
| Optimized mobile policy | Same client, VPS, URL, size, and NP/2 profile selected HTTPS | 110.10 / 101.70 Mbit/s | ✅ | Live connection policy and data path verified |
| Optimized desktop default | Profile omitted `carrier_policy`; strict loader applied `performance` and server logged HTTPS | 97.54 / 98.18 Mbit/s | ✅ | Backward-compatible SOCKS runtime default verified live |
| Direct route baseline | Three 25 MB direct downloads | about 97–111 Mbit/s | ✅ | Optimized NP/2 is within route variance |
| Raw UDP route | 100 Mbit/s offered from VPS to Mac | 28.84 Mbit/s received | 🟠 High | Keep UDP carriers as fallbacks, not the default on this route |
| Raw UDP route | 25 Mbit/s offered from VPS to Mac | 17.80 Mbit/s received | 🟠 High | Consistent with HTTP/3/WebRTC plateau |
| Raw UDP route | 10 Mbit/s offered from VPS to Mac | 10.01 Mbit/s received | ✅ | Confirms a path-dependent loss/policing threshold |
| Cover overhead | 250,462,452 real wire bytes; 1,192,438 padding; 3,904 dummy | about 0.48% | ✅ | No cover reduction required |
| Cell codec | 32 KiB encode/decode benchmark | about 1.8–3.4 GB/s | ✅ | Crypto/framing has ample capacity headroom |
| Mosaic classifier | Three benchmark samples | about 60 ns/op, 0 allocations | ✅ | Classifier is not a throughput limiter |

The controlled A/B improvement is approximately 5.7x. This is specific to the
measured route and must not be presented as a universal throughput multiplier.

## 3. Risks

| Risk | Impact | Status |
|---|---|---|
| Physical iPhone throughput has not yet been measured with the rebuilt signed app | Final device result may differ from the Mac harness | 🟡 Pending user build |
| A network that blocks HTTPS may wait through its configured HTTPS deadline before UDP fallback | Slower fallback connection, but no loss of reachability | 🟡 Bounded by profile timeouts |
| UDP path quality varies by carrier, access network, and VPS provider | HTTP/3 may outperform HTTPS elsewhere | 🟡 Keep per-carrier diagnostics and benchmarks |
| A future regression could reintroduce UDP-first mobile wiring | Speed loss without protocol failure | 🟢 Covered by carrier-order tests and live diagnostics |

## 4. Recommendations

1. Build the app from the refreshed Mac project and confirm diagnostics report
   `carrier=https` on the current Wi-Fi/LTE route.
2. Run three speed tests on the physical iPhone with the same server and compare
   medians, not a single peak result.
3. Repeat one connect/disconnect and one Wi-Fi/LTE transition to verify bounded
   fallback and immediate cancellation during VPN stop.
4. Retain HTTP/3 and WebRTC because they remain valuable when TCP/TLS is blocked
   or when another network has a high-quality UDP path.
